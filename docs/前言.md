# 前言

- 首先，因为目前能看到的基于 mjlab 的项目采用的为 Isaac Lab 那套 **Manager\-Based API；**个人认为比较臃肿，同时代码文件结构很乱；**难以快速魔改与断点调试**：大量的动态分发和反射包装破坏了代码的可追踪性；

- 所以该项目旨在构建一个`legged_gym` 风格的 mjlab 训练框架：

  - 剥离 `mjlab` 的所有 Manager 抽象，保留底层的 MuJoCo Warp GPU 物理仿真引擎，并在上层重写类似 ETH `LeggedRobot` \+ `LeggedRobotCfg` 的单体向量化环境

- 再来看看两者的优缺，对比找到自己想要的：

  - **Manager\-Based 架构：**

    - 优点：

      - **模块化极高**：观测、奖励、事件高度解耦，像搭积木一样复用，适合机械臂、多任务等复杂场景。

      - **配置驱动友好**：调参、换任务只需改 YAML/Dataclass，不用动底层核心代码。

    - 缺点：

      - 各模块独立计算，导致坐标转换、速度投影等公共物理量被反复重复计算

      - 加历史观测（History Buffer）、动作延迟、特权 Critic 极别扭；模型结构难以直接对齐 C\+\+ 实机部署接口

      - 封装层级深、反射和动态分发多，断点跟踪物理状态很痛苦

  - **单体 Tensor 架构：**

    - 优点：

      - **极速且无计算冗余**：公共动力学量一次性算完，全局直接共享张量切片，GPU 吞吐和运行效率拉满。

      - **原生对齐 Sim2Real**：环境内的 Observation 拼接格式与 C\+\+ 推理端的 Sensor Buffer 1:1 一致，零落地转换成本。

      - **算法魔改极快**：写 RMA、HIMLoco 或自监督估计器，只需维护几个 Tensor 队列（如 `torch.roll`），几行代码搞定。

    - 缺点：

      - 所有逻辑、状态和控制全塞在一个大类里，动辄上千行代码，不易分模块维护

      - 抽象拓展成本较高，换一个任务等需要大量重写环境
